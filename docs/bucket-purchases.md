# Spending bucket purchases

A spending bucket has a budget (`target_amount`), spent amount (`current_amount`), and remaining reservation (budget minus spent). Adding a purchase replaces that much of the reservation with the actual cash transaction. It does not create another cash transaction when an existing bank or manual transaction is selected.

The bucket detail flow offers a posted bank transaction, existing manual transaction, or new expense. Purchases must fit the remaining budget. Full buckets require Adjust budget; closed buckets require Reopen. Neither action happens automatically. Viewers and archived buckets retain read access to history. Historical split purchases show their own bucket allocation separately from full transaction cost; earlier spending without loaded transaction history remains an explicit remainder.

## Atomic persistence

The migration ending `_add_bucket_purchase_flow.sql` adds authenticated, household-editor RPCs for add, remove, update, delete, replacement, and budget adjustment. They validate household and budget ownership, current target state, transaction assignment, dates, amounts, account ownership, and remaining funds under row locks. New expense creation and allocation share a transaction. Stable transaction IDs make retries idempotent; conflicting intents fail without orphan transactions.

The existing reconciliation ledger and `private.planned_reconciliation_bases` remain authoritative. Canonical aggregation computes spending buckets from their preserved base plus actual allocations. Historical exact/full settlements no longer fill a later increased budget. Decisions and savings retain their existing closing rules. The older progress trigger delegates to that same aggregate.

A manually recorded purchase can later be explicitly replaced with its posted checking charge. The existing goal reconciliation moves to the bank transaction; the manual representation is hidden, with snapshots retained for undo. Only the actual variance changes spending. Undo restores both original representations and the manual allocation atomically. Existing pending links created before bucket attachment survive posting; explicit ready links permit the existing cross-month handoff. Unrelated purchases are never automatically merged.

Remove from bucket retains Activity cash. Delete first removes/restores the allocation and then soft-deletes the selected cash representation atomically. Activity edits of linked manual purchases update the allocation and transaction together. Bank and legacy split edits require removing the allocation first. Closed or routed bucket safety remains enforced. Legacy overspent buckets can reopen, close, and reduce or remove purchases without changing their target; any changed budget must still cover live spending. Budget edits use compare-and-swap on budget fields and preserve live spending; stale clients cannot overwrite spending with an old form value.

Plaid candidates require the canonical retained checking account identity; historical inactive identities remain usable. Unknown and nonchecking bank accounts are rejected. Manual and statement entries preserve the existing ledger semantics, including the normal active household account rule for new/manual account selection.

## Verification

`node scripts/test-bucket-purchases.cjs` runs against an isolated local PostgreSQL 17 container (`flowledger-bucket-purchases` by default). It creates and drops its own database, loads checked-in schema-only baseline fixtures with source hashes, discovers the migration by suffix, and runs real SQL. No production rows or credentials are required.

The initial verification passed 68 accounting, role, retry, account, pending-link, and legacy RPC assertions, plus four simultaneous-session scenarios: duplicate stable ID, competing remaining budget, budget shrink against a purchase, and posted handoff against manual removal. Legacy posted exact/split review and undo execute the actual prior RPC definitions. Focused TypeScript tests cover combined reservation previews, purchase eligibility/history, UI flows, existing pending replacement, and ordinary transaction previews. Browser and complete-suite results follow.

Browser verification covered the complete owner journey at 320, 390, and 1200 pixels: select a $100 bank charge, select a $55 manual charge, record a $75 purchase, increase the budget to $1,500, and remove the $100 bank allocation. The final bucket correctly showed $480 spent and $1,020 remaining. Owner, viewer, and empty-state checks at 390 and 1200 pixels covered full and closed buckets, reopening, over-budget purchases, archived history, and read-only controls. Phone summary amounts display in full rather than truncating.

Navigation checks verified repeated purchase journeys, transaction and budget editor cancellation, picker X-close, and browser Back through picker, detail, bucket list, and Settings. Full-bucket close confirmation is local to the detail: Cancel or Back keeps the bucket open and retains its details; confirmation closes it with no release. If a concurrent budget increase creates a remainder, confirmation refreshes the detail without closing; the next explicit Close opens the normal remainder choices. This remote-change handoff was verified through Back and a subsequent explicit close, including the exact released amount. Partial close cancellation and Back retain details, and confirmation releases only the unspent remainder. Focused component tests cover failed-save retry, stable new-purchase IDs, duplicate taps, access/scope changes, and retaining a failed close confirmation. These browser checks used fictional local fixtures and recorded no external writes or page errors; complete-suite and release verification are recorded separately.

Final `pnpm run verify` passed all 1,904 tests: 217 API, 403 Edge, 37 release, 1,242 mobile, and five serial performance checks. All workspace typechecks, web export and artifact copy, guide validation, and configuration checks passed. The production dependency audit reported the same three previously ignored high-severity findings, with no new findings. Android Hermes export passed, and Expo Doctor passed all 18 checks.
