# Free/Pro household access and Flo allowance

Source candidate; hosted application belongs to the parent release gate.

The migration captures existing households in a private version-1 planning grant without changing `household_plans`, existing permanent grandfathered Pro or billing records. The fixed grant retains existing planning, local saved scenarios/comparison, historical reports and Flo chat/creation; it never substitutes for actual Pro bank/cloud capabilities. New households use Free core tools with a shared ten-chat monthly preview. New paid Pro households receive 300 monthly chat requests shared by their members. Existing founders/admin Pro/permanent grandfathered Pro keep the existing configured per-user daily cap in Edge; the read RPC's day100 is informational default metadata and adds no new enforcement.

`get_household_feature_access(uuid,text)` is an authenticated invoker wrapper over a private implementation. It checks the actual user exists, active household and current member role; admin preview is allowed only for verified feedback admins. Actual stored plan/source remain in the response during preview. Client-supplied metadata, prices, limits and founding claims never grant access.

Monthly quota uses private RLS-enabled counters and reservation receipts with no direct client/service table grants. Service-only reserve/refund RPCs validate the trusted Edge actor and captured household, choose limits and UTC windows server-side, and serialize increments. Edge generates each receipt ID. Reusing charged, denied, refunded or legacy IDs cannot authorize a second provider call. Monthly refunds are idempotent and target only the receipt's original actor/household/month, including a legitimate active-household switch during a failed provider call; they cannot make a counter negative. The existing rate/daily safety controls remain in Edge.

The original canonical Flo creation body is preserved except for a feature check at its verified receipt/new-write boundary. Existing exact committed receipt replays survive subscription downgrade; new writes require current editor access and Pro/founding creation capability. Recurring-bill proposal confirmation has the same new-write gate after its committed-result replay. Source guards fail migration if those proven boundaries have changed. The existing role/scope, schema validation, idempotency and financial writes are not replaced.

Cloud scenario SELECT is member-only and editor DELETE remains available after downgrade; actual Pro/editor INSERT/UPDATE and the protected-definition trigger remain unchanged. Existing Review Center/bucket lifecycle/reversal entitlement is untouched. No saved scenario or financial row is removed by the migration.

Verification: the actual PostgreSQL integration runner passed 80 assertions across founder/new Free/paid/admin/permanent Pro/viewer/outsider/deleted-user cases; active scope, private ACLs, preview authorization, shared and concurrent limits, duplicate/refund/period behavior, canonical creation/proposal replay, retained cloud data and unchanged bucket recovery were tested with disposable fictional records only. Command: `FLOWLEDGER_FREE_PRO_TEST_CONTAINER=flowledger-free-pro-test node scripts/test-free-pro-entitlements.cjs`. The runner discovers the migration by suffix, allowing its CLI-generated timestamp to be aligned to the observed hosted migration version without changing SQL bytes.

Rollback requires coordinated old frontend and old Flo Edge restoration. Retain founding grants, counters, receipts, cloud data and all financial records. Reverse only the newly inserted canonical feature guards at their exact verified boundaries if restoring the old Founding Free creation behavior; do not replace a newer financial implementation wholesale. Leave the member read/editor cleanup policies in place to preserve data access. Restoring only an old frontend while retaining new creation gates may show a new Free household an upgrade denial until refresh. No billing/checkout/public-bank readiness switch is enabled by this migration.

Current Supabase function/permission guidance and changelog were checked. The new helpers use explicit grants, invoker public wrappers, private definer implementations, empty search paths and full scope checks. New private tables deliberately deny all direct client access. The hosted release must compare advisors and verify the catalog/function boundaries/ACLs without customer financial test writes.
